# Phase 5 security assessment — 2026-10-13

Scope: isolated Supabase project `praluwpaundvwmifaije`. No infrastructure, secrets, Auth settings, migrations or Edge deployments changed.

## Endpoint abuse protection

**Public employee pilot: NO-GO.** The public Supabase function is directly reachable. CORS, Turnstile, body deadlines and atomic database quotas protect different boundaries; none establishes upstream availability protection. Pages WAF rules cannot protect requests made directly to the Supabase hostname. The current handler ignores client IP headers, which avoids trusting spoofable identity.

Recommended minimal next design, subject to separate approval: route just the anonymous intake POST through a small Cloudflare Worker on an existing owned, proxied domain. Keep the existing ITCare URL and Admin paths. Apply path-scoped Cloudflare WAF/rate rules before Worker execution, bound streamed upload bytes and deadlines, remove client-supplied forwarding/authentication headers, and forward only to the fixed isolated function. Retain Turnstile verification in the Edge Function; do not consume a token twice. Keep hostname/action checks and SQL admission/idempotency unchanged.

Require a dedicated random transport secret on Worker and Edge. The Worker replaces the transport header rather than forwarding a client value. The Edge checks it before body parsing, Turnstile, ingress RPCs or database access, failing closed when absent or wrong. TLS protects this server-to-server header; never put it in VITE configuration, browser responses or logs. Rotate it separately from any Supabase API key. The Worker needs no Supabase service-role key. A bounded, timestamped HMAC envelope is a possible later hardening if replay of captured transport requests is in scope, but body hashing adds CPU/memory cost and is not needed merely to authenticate the forwarder.

Do not use `X-Forwarded-For` or a `CF-Connecting-IP` header supplied to the direct Supabase URL as a rate-limit identity. Cloudflare WAF can use its own observed `ip.src` at the controlled ingress; NAT users share that limit, so avoid aggressive thresholds. Keep the database quota as the atomic admission authority. Cloudflare counters can lag and are not an exact global admission mechanism. [Cloudflare rate rules and limitations](https://developers.cloudflare.com/waf/rate-limiting-rules/).

Residual risk: an attacker can still call the direct Supabase function without the transport secret. Early rejection protects database work but may still consume Supabase gateway/function invocations and shared project quotas. A proxy does **not** close that origin or prove DDoS resistance. Obtain provider confirmation/evidence about direct-origin ingress, invalid-request accounting, isolation and available limits. Keep public-pilot NO-GO until the direct-origin availability risk is demonstrably contained. Supabase database network restrictions apply to Postgres/pooler rather than HTTPS APIs and do not solve this problem. [Supabase restrictions](https://supabase.com/docs/guides/platform/network-restrictions).

Costs checked against current documentation: Workers Free includes 100,000 requests/day and 10 ms CPU/invocation; its cap is an availability risk and upload handling must be measured. Workers paid starts at $5/month, with 10 million requests and 30 million CPU ms included, then usage charges. Free Cloudflare zones have one restricted rate rule; stronger bot/rate features can require another plan. Do not infer that Workers paid includes paid WAF/Bot Management. Existing domain/account entitlement must be checked before quoting an all-in cost. [Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/), [WAF availability](https://developers.cloudflare.com/waf/rate-limiting-rules/#availability).

Alternatives: retain the present isolated preview for synthetic QA at no new infrastructure cost; obtain a provider-supported origin restriction if available (capability/cost unverified); or separately review relocating only intake execution to Cloudflare to eliminate the exposed Supabase intake invocation path. That last option carries a broader handler/credential review and is not the immediate UI fix. A paid Supabase upgrade or a proxied custom hostname alone is not evidence that the old origin cannot be abused.

Deployment plan: approve exact Worker/Edge changes, domain route, dedicated transport secret and any paid plan separately; verify provider origin restrictions/accounting first; deploy to isolated resources only; run bounded bypass/header-spoof/body-limit/Turnstile/retry/quota/anonymous-upload/Admin checks; record real ingress metrics and rejection location; then review public-pilot readiness. Keep a manual disable/rollback procedure and budget/usage alerts. Never fall back to unguarded direct intake if the Worker fails. No such resources or settings were created here.

## Password security

Live project organization `lxrclbjsgoweuyxlscat` reports `free`/`tier_free`. The live security advisor reports `auth_leaked_password_protection`: disabled. Official documentation states that leaked-password protection is available on Pro and above. It is unavailable on this Free plan; enabling it requires a paid upgrade. Pro starts at $25/month per organization; compute for additional projects and usage can add charges. There is no separate leaked-password feature charge shown in the cited pricing, but this is not a promise of an all-in $25 bill for this organization. No upgrade or setting change was performed. [Password security](https://supabase.com/docs/guides/auth/password-security), [Pricing](https://supabase.com/pricing).

Free mitigations: owner sets a long, unique password generated/stored in a password manager, checks compromise privately, and keeps test credentials separate from other accounts. Limit active IT accounts and distribute Admin access only to approved testers. Supabase basic TOTP MFA is included on Free, but this repository currently has no MFA enrollment/challenge flow or AAL2 RLS requirement; provider availability is not evidence of enforced application MFA. Add both UI and server authorization enforcement in a separately scoped approved change. Hiding the Admin link or restricting only its Pages path cannot secure direct Supabase Auth/REST. [MFA implementation and RLS](https://supabase.com/docs/guides/auth/auth-mfa), [Free MFA entitlement](https://supabase.com/pricing).

Advisor findings for private intake tables with RLS/no policies are intentional deny-all for public roles. Four authenticated security-definer RPC warnings require continued review of authorization inside each function; live denial probes passed for `update_ticket` and `set_employee_active`, but do not erase the advisor warnings or establish every legacy RPC safe.
