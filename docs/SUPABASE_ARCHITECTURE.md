## Boundary and data flow

`context/itcare` selects a real provider by default. Only development with `VITE_ITCARE_DEMO=true` loads the demo provider and MSW. Production ignores that flag; missing configuration displays a disabled login with a configuration error. No mock fallback occurs after failed authentication or queries. SDK calls live in `integrations/supabase/gateway.ts`; typed DTOs and mapping/upload orchestration live in `services/itcare/service.ts`. UI continues using Vietnamese statuses; PostgreSQL stores stable English codes.

Email/password authentication uses the official SDK with persistent sessions and token refresh. Role and active status come from `profiles`, never the login URL, local demo identity or auth metadata. Auth callbacks defer database reads to avoid calling SDK methods while its auth lock is held. Protected routes wait for profile restoration. Logout clears the user and its separate SWR cache. RLS remains the authority if a browser changes local state.

SWR refreshes every 30 seconds, on focus and reconnect, and after mutations. This deliberately avoids a second realtime subscription/cache architecture. Photos use 120-second signed URLs refreshed with data. Polling can delay UI changes; PostgreSQL rejects new unauthorized operations immediately. Existing signed URLs can remain usable until expiration. Supabase access tokens can remain valid after logout until their expiry; client cache removal is not token revocation.

## Create a separate test project

1. Create a new disposable Supabase project in your own account. Do not use an unknown existing production database.
2. Disable **Allow new users to sign up** in Authentication settings. Disable anonymous sign-ins. Configure your actual local/pilot site URL and redirect allowlist; local examples are in `supabase/config.toml`. Do not expose public registration.
3. For a **new empty test project only**, run `supabase/migrations/20261010075402_itcare_initial.sql` once as its trusted administrator. It creates tables, transactional RPCs, grants, RLS and the private bucket. **Do not run it again on existing `itcare-dev`**: the remote schema/history already matches this version; see `MIGRATION_HISTORY.md`. Keep exposed schema `public`; do not expose `itcare_private`. For local CLI, provision Docker and apply migrations to a new local test database; that CLI/Docker route remains NOT TESTED here.
4. Copy `.env.example` to `.env.local`. Fill `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` from the test project's settings. Use a publishable key (or legacy **anon** key), never a secret/service-role key. Vite variables are browser-visible; RLS provides authorization. Leave `VITE_ITCARE_DEMO=false`.
5. Run `npm ci`, `npm run dev -- --host 127.0.0.1 --port 5174`. Restart Vite after changing environment variables. Configure the SPA host to serve `index.html` for application routes before any deployment.
6. Run `npm test`, `npm run lint:itcare`, `npm run build`, `npm audit`; then execute the cloud acceptance checklist in `PHASE_2_QA_REPORT.md` with synthetic users.

For visual demo only, set `$env:VITE_ITCARE_DEMO='true'` in PowerShell before `npm run dev`. Remove it (`Remove-Item Env:VITE_ITCARE_DEMO`) before real-data testing. Demo credentials appear only in this explicitly enabled development mode.

## First IT and synthetic account provisioning

Use the trusted Supabase Dashboard Authentication **Add user / Create user** operation. Create synthetic Employee A, Employee B, an inactive employee and IT with distinct test emails and separate strong passwords generated by your password manager. Confirm test accounts administratively when appropriate. Never commit or paste those passwords into code, SQL, screenshots or chat. Use an approved secure channel for credentials.

The auth trigger creates every profile as **inactive employee**, even if user metadata requests IT privileges. Copy the new IT user's UUID from the Dashboard and run this as the trusted database administrator, substituting the UUID and synthetic display fields:

```sql
update public.profiles
set full_name = 'Test IT', department = 'IT', role = 'it', active = true
where id = 'REPLACE_WITH_AUTH_USER_UUID'::uuid;
```

Activate A/B with the same administrator-only SQL, retaining `role='employee'`. Leave the inactive account disabled. Afterwards active IT can activate/deactivate existing employees through the restricted RPC; browser clients cannot promote roles or create accounts. Do not provision IT by modifying user metadata or exposing an admin key to this SPA. Invitation/password-reset completion screens are deferred; this phase uses administrative account creation rather than claiming an invitation flow exists.

## Draft cleanup and test reset

Failed uploads leave a reserved, private draft for retry with the same request UUID. Drafts do not appear in the IT inbox or as submitted tickets. Reserved object paths cannot become unrelated public files. Do not delete rows from `storage.objects` with SQL: that does not remove actual stored bytes.

For a disposable test project, use the trusted Dashboard Storage UI to delete objects in `incident-photos` first, then use administrator SQL to delete the chosen synthetic tickets (dependent attachments/comments/events cascade). To clean abandoned drafts, inspect tickets with `submitted_at is null` and `created_at < now() - interval '7 days'`, list their `ticket_attachments.storage_path`, remove those objects with the Dashboard or trusted server-side Storage API, then delete those draft tickets. Do not purge fresh drafts during retries. Scheduled cleanup is deferred; assign an administrator and retention policy before a pilot.

To reset synthetic users in a disposable project, remove all their test objects/tickets first (including any tickets retaining their comment/event author references), then delete the corresponding `public.profiles` rows as trusted administrator before deleting auth users via Dashboard. The auth/profile FK deliberately restricts deletion while profiles remain. Prefer deactivating accounts where history must be retained. Never run a wholesale reset in production. Database sequence gaps from failed drafts are expected and must not be renumbered.
