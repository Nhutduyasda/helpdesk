## Pages Functions versus standalone Worker

Prefer a file-routed Pages Function `functions/api/intake.ts` on the existing isolated preview after separate approval. It runs in Workers runtime and offers same-origin `/api/intake` without a paid/custom domain or additional Worker project. Current deployment uses Wrangler `pages deploy dist`, not dashboard drag-and-drop: Wrangler supports Functions with Direct Upload; dashboard Direct Upload does not. The Functions source must be present when Wrangler builds the deployment; the current deploy job downloads only `dist`, so future packaging must explicitly compile and include the function artifact or supply reviewed source in that job. This source/deployment workflow change has not been made.

Advanced-mode `dist/_worker.js` is another supported packaging option, but must explicitly forward static requests to ASSETS and preserve SPA behavior and headers. File routing is smaller for one API. Keep `_routes.json` scoped to `/api/intake` so static assets do not unnecessarily invoke compute. Verify that custom response headers apply to Function responses; Pages `_headers` alone is not a substitute. A standalone Worker would add routing/cross-origin configuration and offers no escape from Free CPU limits. No paid domain needed for preferred Pages integration.

Sources: [Pages Functions](https://developers.cloudflare.com/pages/functions/get-started/), [Direct Upload](https://developers.cloudflare.com/pages/get-started/direct-upload/), [advanced mode](https://developers.cloudflare.com/pages/functions/advanced-mode/), [Functions pricing](https://developers.cloudflare.com/pages/functions/pricing/). ## Credential assessment

Existing `intake_precheck`, `prepare_public_ticket` and `finalize_public_ticket` execute privileges are service_role-only. Existing browser anon/authenticated grants cannot substitute. Private Storage orchestration needs privileged upload and duplicate-byte download; use a server-only SDK client. Existing server credential must never enter frontend, artifact/public variables or logs.

[Supabase API key documentation](https://supabase.com/docs/guides/getting-started/api-keys) confirms secret keys resolve to service_role and bypass RLS; dedicated secret-key naming/rotation does **not** narrow database permissions. Prefer an independently revocable secret key for a future Worker if authorized and compatible; this is still broad privileged access. No credential read/copied/generated/rotated here.

A genuinely narrower Postgres role would require explicit RPC grants, controlled role authentication and a Storage authorization design for exact reserved paths (including retries). A direct Postgres credential alone does not grant Storage API access. A signed-upload broker could keep broad secrets out of Worker, but changes trust/validation/idempotency and potentially grants or another origin execution path. These alternatives need a new reviewed design and separately approved grants/migrations/credentials. Do not weaken anon RLS or grant intake RPCs to browser roles to avoid the secret.

### Paid fallback assessment — recommendation B, subject to separate implementation review

Recommend **Workers Paid for any future implementation**, after a dedicated bounded memory/concurrency test and real SDK profiling. Paid changes the default HTTP CPU ceiling from 10 ms to 30 seconds and can be configured as high as 5 minutes; the current estimate is comfortably within execution time if hosted results are comparable. It does **not** raise the 128 MiB isolate memory limit. The measured ~105 MiB backing snapshot means one max upload might fit, but peak and two overlapping max uploads are not proven; use streaming and avoid buffering/copy chains, then measure two concurrent synthetic requests locally before any cloud test. Preserve all image/hash checks and fail closed.

Cloudflare Workers Paid pricing is $5/month and includes 10 million requests and 30 million CPU milliseconds/month; additional requests are $0.30/million and additional CPU $0.02/million milliseconds (check current account pricing at purchase time). At ~10 genuine submissions/month, 10 Worker invocations and <0.2 CPU seconds each (even at 200 ms) is ~2 seconds monthly, well within included usage; abusive traffic/account-wide workloads change this. Requests to the Function may include one invocation, and separate outbound Siteverify, Supabase RPC, and image Storage requests are subrequests, below 50/request for the expected 0/1/3-image flow. Validate exact binding/network accounting with a reviewed hosted test. Same-origin Pages Functions remain supported with Wrangler Direct Upload packaging; no custom domain charge is inherently required.

Cost controls for a future Paid account: confirm Workers plan and request/CPU quotas, set dashboard billing notifications/usage alerts at account thresholds, inspect Workers invocation and overage metrics weekly during pilot, cap voluntary test cases, and pause nonessential QA before overage. Threshold notification may not be a hard spend cap; verify account billing controls. No Paid plan change/purchase or alert configuration has been made.

Paid does not change Supabase credential risk. Intake RPCs and private Storage currently need privileged server operations. A Supabase secret key still maps to `service_role` and bypasses all RLS, even when separately named/revocable. Store it only as a Worker secret binding; keep Turnstile secret server-side; never include secrets in Vite variables, browser, Git, build, CI output or logs. Restrict secret access, isolate preview bindings, rotate through overlap, sanitize logs. No narrower storage/RPC credential is verified. A custom Postgres role is not a substitute for Storage API privilege; it requires a separately reviewed authorization/upload design. Paid is a technically plausible CPU path, **not cloud-ready** until memory/concurrency, SDK/runtime and security acceptance pass.

**Decision: B — Free is not practical under existing max-size features; recommend a Paid implementation with the stated controls.** This is based on a local lower-bound gap, not a hosted CPU claim.
